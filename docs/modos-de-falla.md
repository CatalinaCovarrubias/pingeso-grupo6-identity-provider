# Modos de falla — MS Usuarios y Roles

Cada falla posible del servicio, qué la impide y cómo se verifica. Este documento se escribe
antes de programar cada parte y se actualiza cuando aparece una falla nueva.

Estado:

- **P**: prevención implementada y probada.
- **I**: implementada, falta la prueba indicada.
- **D**: diseñada, falta implementarla.
- **A**: riesgo aceptado y documentado.

Las pruebas nombradas son pruebas Go (`go test ./...`). Las que dicen "e2e" son de la Tanda 6,
contra el binario real y PostgreSQL.

## 1. Disponibilidad

| ID    | Falla                                                | Qué la impide                                                                                                                                                           | Cómo se verifica                                                                                                                                              | Estado |
| ----- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| MF-01 | PostgreSQL caído o sin red                           | `/readyz` responde 503 (problem+json) si el ping no contesta en 2 s                                                                                                     | `TestReadyzConBaseCaida` y prueba manual deteniendo el contenedor                                                                                             | P      |
| MF-02 | Falta una variable de entorno                        | La configuración se valida al arrancar y el proceso termina con un error que la nombra. Incluye `JWT_EMISOR`, `JWT_AUDIENCIA` y `JWT_TTL` (entre 1 min y 24 h)          | `TestCargarFallaSiFaltanVariables`, `TestCargarFallaConTTLInvalido`, `TestLevantarServidorFallaSinConfiguracion`                                              | P      |
| MF-03 | La API arranca antes que las migraciones             | Compose: `backend` espera `service_completed_successfully` de `migrate`                                                                                                 | `docker compose up` desde cero                                                                                                                                | P      |
| MF-04 | Consulta lenta deja la petición colgada              | Timeout de 5 s en cada llamada a la base y `ReadHeaderTimeout` en el servidor                                                                                           | e2e con consulta bloqueada (Hito 2)                                                                                                                           | D      |
| MF-05 | Llave de firma ausente, ilegible o débil al arrancar | `JWT_LLAVE_PRIVADA_ARCHIVO` es obligatoria en test y prod. El proceso termina si el PEM no carga, no es RSA o tiene menos de 2048 bits                                  | `TestLlaveObligatoriaFueraDeDesarrollo`, `TestLevantarServidorFallaSinLlaveEnProduccion`, `TestLevantarServidorFallaConLlaveInvalida`, `TestCargarLlaveFalla` | P      |
| MF-06 | En dev, un reinicio invalida los tokens emitidos     | Sin llave en dev se genera una en memoria y se avisa en el log. Los consumidores vuelven a leer el JWKS ante un `kid` nuevo; para tokens estables se usa una llave fija | `TestLevantarServidorEnDesarrolloGeneraLlave`; documentado en `docs/jwt-de-prueba.md`                                                                         | A      |

## 2. Autenticación

| ID    | Falla                                                                              | Qué la impide                                                                                                                      | Cómo se verifica                                                                                                     | Estado |
| ----- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------ |
| MF-10 | Credenciales incorrectas                                                           | Respuesta 401 genérica: no revela si existe el correo. El 403 de cuenta no activa solo aparece con la contraseña correcta          | `TestIniciarSesionIncorrectaNoRevelaElCorreo`, `TestLoginIncorrecto`, `TestIniciarSesionConCuentaNoActiva`           | P      |
| MF-11 | Ataque de fuerza bruta                                                             | Bloqueo temporal tras N intentos fallidos por correo                                                                               | e2e: N+1 intentos fallidos devuelven 429                                                                             | D      |
| MF-12 | Diferencia de tiempo revela si existe el correo                                    | Si el correo no existe, se compara igual contra un hash bcrypt ficticio del mismo costo                                            | Prueba de tiempos en el e2e de login                                                                                 | I      |
| MF-13 | Token alterado o firmado con otra llave                                            | Verificación RS256 con la llave pública del `kid`; un `kid` desconocido se rechaza                                                 | `TestRechazaTokensInvalidos` (tokens y api): payload alterado, sin firma, otra llave, otra llave con el `kid` propio | P      |
| MF-14 | Token vencido                                                                      | `exp` obligatorio y validado, con 30 s de tolerancia                                                                               | `TestRechazaTokensInvalidos`: vencido → 401                                                                          | P      |
| MF-15 | Robo del token desde el navegador                                                  | Cookie `sesion` `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. El login no devuelve el token en el body. Prohibido `localStorage` | `TestLoginCorrectoFijaLaCookie`; la regla contra `localStorage` va en el lint del front (Tanda 2)                    | P      |
| MF-16 | Llave privada filtrada                                                             | La llave entra solo por archivo (`.secretos/` y `*.pem` ignorados por git y Docker). Rotación con nuevo `kid` publicado en el JWKS | Procedimiento de rotación y su prueba                                                                                | I      |
| MF-17 | Otros servicios no pueden leer el JWKS                                             | `/.well-known/jwks.json` sin autenticación, con `Cache-Control: max-age=300`; los consumidores lo cachean con keyfunc              | `TestJWKSPublicaElKidDeFirma` (tokens y api); e2e del endpoint                                                       | P      |
| MF-18 | Confusión de algoritmo (`alg: none`, o HS256 usando la llave pública como secreto) | El validador fija `RS256` como único algoritmo aceptado                                                                            | `TestRechazaTokensInvalidos`: `alg none` y `HS256 con llave` → inválidos                                             | P      |
| MF-19 | Desfase de reloj entre servicios                                                   | Tolerancia de 30 s en `exp`, `nbf` e `iat`. Un token emitido más de 30 s en el futuro se rechaza                                   | `TestAceptaDesfaseDeReloj`, `TestRechazaTokensInvalidos` (emitido en el futuro)                                      | P      |

## 3. Autorización y datos

| ID    | Falla                                                                    | Qué la impide                                                                                                                                                                                     | Cómo se verifica                                                                                                         | Estado |
| ----- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------ |
| MF-20 | Usuario sin permiso accede a un recurso                                  | Cada operación declara su permiso en `x-permiso`; el middleware responde 403. Una operación sin permiso declarado exige sesión (falla cerrado)                                                    | `TestUsuarioSinPermisoRecibe403`, `TestCadaOperacionDeclaraSuPermiso`; matriz por rol en `acceso_test.go` (Tanda 5)      | I      |
| MF-21 | Usuario se asigna a sí mismo un rol con más permisos                     | Asignar roles requiere `roles:administrar`. `PATCH /api/usuarios/{id}` solo cambia correo y estado, y requiere `usuarios:administrar`                                                             | `TestUsuarioSinPermisoRecibe403` (operador → `PUT .../roles` = 403); `acceso_test.go`                                    | P      |
| MF-22 | Dos registros simultáneos con el mismo correo                            | Correo normalizado a minúsculas y único sin distinguir mayúsculas; el segundo recibe 409. En PostgreSQL: índice único sobre `lower(correo)` (Tanda 4)                                             | `TestCreacionConcurrenteConElMismoCorreo` (store en memoria); e2e concurrente contra PostgreSQL                          | I      |
| MF-23 | Se elimina un rol que tienen usuarios                                    | El service rechaza con 409 si el rol está asignado                                                                                                                                                | `TestRolesProtegidosYAsignados`, `TestCrudDeRoles` (api)                                                                 | P      |
| MF-24 | Se elimina o bloquea al último administrador                             | Regla de negocio: siempre debe quedar al menos un administrador activo (al desactivar, bloquear o quitar el rol). En memoria la verificación no es atómica: la Tanda 4 la hace en una transacción | `TestSiempreQuedaUnAdministradorActivo`, `TestNoSeDesactivaAlUltimoAdministrador`; e2e concurrente                       | I      |
| MF-25 | Datos de entrada inválidos                                               | Validación en el contrato con Huma (tipos, `format`, `minLength`, `maxLength`, `pattern`, `maximum`, `uniqueItems`, `minProperties`)                                                              | Pruebas de cada recurso con datos inválidos → 422 (`TestCrudDeUsuarios`, `TestCrudDeRoles`, `TestPerfiles`)              | P      |
| MF-26 | `POST /api/dev/tokens` expuesto fuera de desarrollo                      | La ruta solo se registra con `API_ENV=dev`; con `test` o `prod` no existe (404)                                                                                                                   | `TestTokensDePruebaSoloEnDesarrollo` (arma el servidor igual que `main`), `TestTokensDePruebaNoExistenFueraDeDesarrollo` | P      |
| MF-27 | Rol revocado o usuario bloqueado mientras tiene un JWT vigente           | El token dura 15 min (`JWT_TTL`); el login de una cuenta no activa se rechaza. Se acepta la ventana de 15 min (decisión D4)                                                                       | Documentado en el contrato y en `docs/jwt-de-prueba.md`; la renovación real vuelve a leer roles (Tanda 4)                | A      |
| MF-28 | Logout no invalida el JWT ya emitido                                     | El logout borra la cookie; el token sigue valiendo hasta su `exp` (15 min). Misma ventana aceptada que MF-27                                                                                      | `TestCerrarSesionBorraLaCookie`                                                                                          | A      |
| MF-29 | Alguien le quita permisos al rol administrador y nadie puede administrar | El rol `administrador` no se modifica ni se elimina (409)                                                                                                                                         | `TestRolesProtegidosYAsignados`, `TestCrudDeRoles` (api)                                                                 | P      |

## 4. Información sensible

| ID    | Falla                                   | Qué la impide                                                                                     | Cómo se verifica                                                                                               | Estado |
| ----- | --------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------ |
| MF-30 | Contraseñas guardadas en texto plano    | Solo se guarda el hash bcrypt (`golang.org/x/crypto`); el hash nunca sale del service             | `TestSeedGuardaHashYNoLaContrasena`, `TestCrearUsuario`                                                        | P      |
| MF-31 | Contraseñas o tokens en los logs        | Logs con `log/slog`: nunca se registran contraseñas, tokens, cookies ni cuerpos                   | Revisión de código y prueba sobre la salida de logs (Tanda 5)                                                  | I      |
| MF-32 | Errores que exponen trazas o SQL        | Errores en formato RFC 9457 con mensajes genéricos; un error desconocido es 500 sin detalles      | `TestReadyzConBaseCaida`, `TestErrorDesconocidoEs500SinDetalles`, y cada prueba de error revisa `problem+json` | P      |
| MF-33 | Secretos subidos al repositorio         | Gitleaks en pre-commit y en el pipeline; `.secretos/` y `*.pem` en `.gitignore` y `.dockerignore` | Commit de prueba con un secreto falso es bloqueado                                                             | D      |
| MF-34 | CSRF sobre endpoints que usan la cookie | `SameSite=Lax` impide enviar la cookie en POST, PUT, PATCH o DELETE desde otro sitio              | Prueba con un `Origin` ajeno cuando exista el front (Tanda 2)                                                  | D      |
